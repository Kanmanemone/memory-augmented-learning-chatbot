# Architecture Decision Records

## 철학
lossy_clone은 원본을 그대로 베끼는 것이 아니라, 개념과 전체 흐름만 참고해서 다시 짜는 연습용 산출물이다. 기능은 한 번에 다 만들지 않고 작은 단위로 순서대로 쌓아 올리며, 매 단계는 그 자체로 동작해야 한다. 디테일보다 "지금 필요한 최소 동작"을 우선한다.

---

### ADR-001: 완전히 독립된 폴더로 개발한다
**결정**: `lossy_clone/` 폴더 밖의 어떤 파일도 import/참조하지 않는다. 필요한 코드는 참고만 하고 직접 다시 작성한다.
**이유**: "폴더를 잘라내서 다른 곳에 붙여넣어도 실행되어야 한다"는 요구사항. 원본과의 결합이 조금이라도 있으면 이식성이 깨진다.
**트레이드오프**: 원본에 이미 있는 코드를 재사용하지 못하므로 초반 구현 속도는 느리다.

### ADR-002: 코드를 수정하지 않고, lossy하게(손실 있게) 따라간다
**결정**: 원본 코드를 읽고 전체적인 개념과 동작 흐름을 참고하되, 세부 구현은 스스로 다시 설계한다. 함수/변수 이름은 기본적으로 원본을 따르고, 이름이 실제로 좋지 않다고 판단될 때만 바꾼다.
**이유**: 목적이 원본을 토씨 하나 안 틀리고 재현하는 것이 아니라 개념을 체화하는 학습 과정이기 때문. 원본에는 데모/실습 목적에 맞춰 다듬어진 세부 로직이 많아서, 그걸 전부 그대로 따라가면 핵심 흐름을 배우기보다 베끼기에 그치기 쉽다.
**트레이드오프**: 원본과 동작이나 일부 이름이 미묘하게 달라질 수 있다 (의도된 손실이다).

### ADR-003: 처음부터 전부 만들지 않고 단계적으로 쌓는다
**결정**: 기능을 한 번에 다 만들지 않고, 작은 단위로 하나씩 순서대로 쌓아 올린다. 각 단계는 그 자체로 동작하는 상태를 유지한 뒤에만 다음 단계로 넘어간다. 어느 단계에 어떤 기능이 포함되는지는 `PRD.md`의 로드맵을 따른다.
**이유**: "첫 시작부터 단계적으로 조금씩" 진행하고 싶다는 요청. 각 단계가 끝날 때마다 동작을 확인할 수 있어야 다음 단계로 넘어갈 근거가 생긴다.
**트레이드오프**: 아직 다루지 않은 단계의 기능은 그 전까지 존재하지 않는다. 의도된 제약이다.

### ADR-004: 실제로 동작하는 LLM 연동을 붙인다
**결정**: 장식적인 optional 연동이 아니라, 실제로 호출되어 대화가 되는 LLM 연동을 만든다. 다만 특정 벤더(Gemini 등)에 고정되지 않도록 연동 지점은 교체 가능하게 분리한다.
**이유**: 원본은 실습/데모 목적으로 일부 구간이 mock이나 고정된(deterministic) 값으로 채워져 있어, 실제로 계속 대화를 주고받는 용도로 쓰기는 어렵다. lossy_clone은 그 부분을 실제로 동작하는 형태로 다시 만드는 것이 목적 중 하나다.
**트레이드오프**: API 키나 네트워크가 없으면 챗봇 자체가 동작하지 않는다. ADR-001의 "독립적으로 실행된다"는 폴더를 옮겨도 코드가 그대로 동작한다는 뜻이지, LLM 호출에 필요한 API 키 같은 외부 조건까지 없앤다는 뜻은 아니다.

### ADR-005: LTM은 summary 하나만 담는 최소 스키마로 시작한다
**결정**: LTM은 `summary`(세션 요약 텍스트) 하나만 담는 최소 스키마로 시작한다. 원본의 `struggles`/`strengths`/`confusions`/`topic_tags`/`embedding` 같은 필드는 지금 넣지 않는다.
**이유**: `PRD.md` 로드맵상 강점/약점/혼란 누적은 3단계(Episodic memory), 임베딩/검색은 4단계 스코프다. 지금 한 번에 넣으면 ADR-003("단계적으로 쌓는다")을 어기게 된다.
**트레이드오프**: 2단계가 끝난 시점에는 세션이 "무엇에 대한 대화였는지"만 남고, "무엇을 어려워했는지" 같은 학습 분석은 3단계 전까지 존재하지 않는다.
